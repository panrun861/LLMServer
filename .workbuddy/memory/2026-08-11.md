# 2026-08-11 工作记录

## Ed25519 签名「传播过程中是否泄露」分析（用户提问）
- **私钥永不外传**：Ed25519 是非对称签名，客户端仅在本地用 private_key 对请求指纹签名，网络上只传 64 字节签名（x-signature 头）+ 6 个头 + body。**私钥始终留在客户端，不会在传播中泄露**（这是签名机制的根本属性）。
- **签名 ≠ 加密**：签名保证「身份真实 + 内容未被篡改」，但不保证「内容保密」。当前部署是**明文 HTTP（8080 直暴露公网，无 nginx/Caddy/TLS）** → 链路上的嗅探者/中间人能看到全部 header 与 body（含 /v1 的对话内容、POST /admin/pllm-tokens 的 subject/name），但**无法据签名反推私钥、无法伪造新请求、无法重放同请求（nonce 防重放）**。
- **结论**：泄露的是「请求内容的机密性」，不是「私钥/认证」。修复 = 在 PLLM 前加 TLS 终止（反向代理 + Let's Encrypt 或 LB 终止），把 http 升级为 https。签名机制本身无需改。
- 复盘点：PLLM 暴露面无 TLS；dashboard 用 ?token= 查询参数也会把 token 写进 URL/日志；/docs 默认暴露完整 schema。建议统一前置 HTTPS。
- **用户概念澄清（重要交互模式）**：用户一度把 Ed25519「签名」等同于「加密」，追问"什么东西加密在请求里面 / 为什么在 header"。已明确纠正：**请求内无任何加密内容**，只有 x-signature 这 64 字节签名(明文传输,不可伪造但可读);签名放 header 是因它是认证元数据(非业务数据)、中间件先验再放行、且签名串已含 sha256(body) 绑定 body 完整性。真正"加密内容"的是 TLS/HTTPS(整条报文加密隧道)。后续涉及认证/传输安全话题时,默认先区分 签名(认证+完整性) vs 加密(机密性),避免用户再次混淆。
- **架构决策结论（用户曾误以为应"换成加密而不是签名"）**：已明确纠正——**签名与加密不是二选一、必须叠加**。Ed25519 签名层负责「客户端身份 + 请求防篡改 + nonce 防重放」，TLS 负责「内容机密性 + 服务器身份 + 响应完整性」。若砍掉签名只剩 TLS：失去客户端强身份、失去请求防篡改/防重放、失去私钥不出门模型。正确动作 = **保留 Ed25519 签名不动，在 PLLM 前加 TLS 反向代理（nginx/Caddy + Let's Encrypt）**，把 8080 收进 https，uvicorn 改为仅容器内监听。用户仍未拍板是否让我落地该 HTTPS 模板。
- **用户已正确综合（本晚收尾）**：用户主动说出"HTTPS 只能保证传输过程的不可见，但还是要密码和这里的私钥和签名"——说明已**正确区分 TLS(仅传输加密/机密性+服务器身份+响应完整性) 与 认证(Bearer密码 + Ed25519私钥/签名)**，理解三者必须叠加而非替换。后续涉及该话题无需再重复签名vs加密基础概念，可直接推进落地(HTTPS 模板/部署)。
- **HTTPS 落地方案（用户问"自己服务器如何保证 https + 后端加什么"）**：已定位 PLLM 应用本体在根 docker-compose.yml 的 `app` 服务(build:., 映射 ${PLLM_PORT:-8080}:8080, 网络 aitube-pllm_default)，与推理栈 docker-compose.remote.yml(stack_default: postgres/vllm/vllm-ocr/litellm/openhands) 是**两套独立 compose**。具体方案：① 同 compose 加 `caddy:2` 服务(发布 80/443, 挂 Caddyfile + caddy_data/config 卷, depends_on app)；② app 去掉对外 ports、改 `expose: 8080` 仅内网给 caddy；③ Caddyfile 用域名+email 自动申请 LE, `reverse_proxy app:8080` + `header_up X-Forwarded-Proto`, 顺带 `request_header -x-local-admin` 防绕过 + 屏蔽 /docs；④ Dockerfile CMD 加 `--proxy-headers --forwarded-allow-ips=*`。硬前提：LE 需域名解析到 35.76.187.215(裸IP不能签, 可用 nip.io 或 tls internal 自测)。Ed25519 签名与 Bearer 代码均不动。另提醒：同机 docker-compose.remote.yml 的 litellm:4000(带 master key)/vllm:8000/postgres:5432/openhands:8888 也 0.0.0.0 裸暴露, litellm 风险更大, 后续需一并收口。用户仍未拍板是否让我写文件落地。
